**本文の地は `.62`。** `#stage` は `position:fixed` なので、文字はその上を
通過していく。海は凪で動いているが、動いているのは雪・光条・魚で、
地の明るさそのものはほとんど動かない。実測（地のいちばん明るい砂に対して）:

| 地の濃さ | 本文 p | 一覧 dd | 見出し h2 | 8.5pxラベル |
|---|---|---|---|---|
| `.945`（前） | 13.6 | 12.1 | 16.6 | 5.4 |
| `.62`（現在） | 11.1 | 10.0 | 13.3 | 7.3 |
| `0`（全透過） | 6.8 | 6.2 | 8.0 | 3.4 |

全透過でも本文は 6.8:1 ある。効いてくるのは 8.5px の欧文ラベルだけなので、
本文の中のラベルだけ `--hud`（.60）から `.80` へ持ち上げてある（計器側は触らない）。
**ここを動かすときは必ず `measure-sheet.mjs` で測り直すこと。見た目で決めない。**

リンク検査は必ず `out/` に対して行う。`public/` を配ると `/becool/` が
無いので、生きているリンクまで404に見える。

**文字のコントラストはCSSの色を見ても分からない。** 3Dの上に乗るので、
背景は毎フレーム変わる絵になる。`measure-contrast.mjs` は各文字の
**外側 2〜9px の帯**を背景とみなして測る。矩形の中の画素を使うと、
白文字のアンチエイリアスを背景と誤認して、地色が暗い場面でも 1.1:1 と出る。

**この環境は約1fps（SwiftShader）。** 潜航は smoothDamp で追従するので、
スクロール位置を変えたあと収束を待つには「フレームが進んだうえで値が
動いていない」ことを条件にする。値だけ見ると同じフレームを2回読んで
「止まった」と誤判定する。

`--tier=high` を付けないと、検証機は hardwareConcurrency が小さいため
必ず low ティアになり、high 側にしかない経路(水面の映り込み)が
一度も動かないまま「通った」ことになる。

`verify.mjs` は**ページの隣をそのまま一時ディレクトリへ配る**。
`index.html` と `vendor/` だけ置くと本文の写真が 404 になり、しかも
遅延読み込みなのでそこまで送るスクロールをした時だけ落ちる
——「デスクトップは通るのにモバイルだけ console エラー2件」という
分かりにくい出方をした。

**「動いていない」ことを測るときは、必ず差分の位置も出す。**
`scripts/degrade.mjs` は reduced-motion の2枚が一致しない時に
差分の画素数と外接矩形を出す。合否だけだと原因の当て推量になり、
実際に魚を止めたあとも一致せずもう1周した（残っていたのは
被写界深度のピントの寄りだった）。

**「静止しているか」を秒で待たない。フレームで待つ。**
この環境は1〜4fps なので、3秒待つのは実ブラウザの 0.05〜0.2 秒に
しかならない。スクロールで飛んだ直後の収束(数フレーム)を
「動き続けている」と誤検出する。`degrade.mjs` は
`__diag.frames` が 40 進むのを待ってから1枚目、24 進んでから2枚目を撮る。
測りたいのは「収束したあと静止しているか」であって「常に静止しているか」ではない。

**「Nフレーム待つ」も決め打ちにしない。「動かなくなるまで」待つ。**
目次の判定は針が目標へ追従し終わるのを 4 フレーム待って読んでいたが、
この環境の実測は 0.2〜1fps まで振れる。遅い回だけ針が途中で止まったまま
読まれ、1行手前(`philosophy`)を指して落ちた —— 中身は何も壊れていない。
`verify.mjs` の `waitDot()` は `#rdot` の位置が動かなくなるまで待つ
（フレームが進んだ上で 0.25px 未満、を3回）。
**落ちたら、まず物ではなく物差しを疑う。**

## 退避の3経路（毎回ここまで確認する）

```
node scripts/degrade.mjs
```

| 経路 | 合格の中身 |
|---|---|
| `prefers-reduced-motion: reduce` | 3.5秒あけた2枚が**完全一致**（差分0画素）。水面と汀の両方で。`timeScale` 0 / 汀線 d=0・θ=0・ずれ0 |
| JavaScript 無効 | 本文 15,024字・h2 11本・リンク7本が読める。**620vhの空白が0に畳まれている**。名乗りが `<noscript>` の静的な見出しとして出る |
| WebGL2 非対応 | 上端に案内、空白0、本文全部 |

**reduced-motion は「演出を止める」ではなく「1フレーム目で完成している」。**
一次遅れが1つでも残ると、海が止まっているのに何かだけが寄り続ける。
窓口は `ease1(k, dt)` と `lag1(t)` の2つだけで、reduced では
係数1・時定数0を返す。**新しく追従を書くときも必ずこの2つを通す**
（`Math.min(1, dt*k)` を直接書かない）。魚だけは時計が2つに割れていて、
位置と姿勢は `timeScale`、出入りの濃度は実時間（濃度まで止めると
alpha が 0 のまま一匹も出てこない。reduced では濃度も即座に当てる）。

**JS無効で畳むのは `html:not(.js)`。** `data-nogl` は JS が立てる属性なので
JS無効では絶対に立たない。`#hud` だけ消すと 620vh の空白（実測5233px）が
残り、本文の前に6画面ぶんの黒が挟まる。空白・暗幕・粒子・boot を畳んだうえで、
`#hud` ごと消える名乗りを `<noscript>` の中に静的に置き直す。

## 潜り終わりの受け渡し — 汀線(ていせん)

海から本文へ渡るところを、フェードではなく**幾何**で繋いでいる。

- ピッチ θ の透視投影では、無限に広がる床の消失線は必ず
  `ndc.y = -tan(θ)/tan(fov/2)` に出る。カメラの高さにも床までの距離にも
  依存しない。**θ=0 なら画面のちょうど垂直中央**。
- 本文シートの上端は、被覆率 c に対して `ndc.y = 2c-1`。
- よって **θ=0 かつ c=0.50 で、砂の消失線と本文の上端罫が同じ1本になる**。

時計は2本ある。**混ぜてはいけない。**

| | 何を駆動するか | 平滑 |
|---|---|---|
| `hpR` | 幾何（ピッチ / シートの見かけの位置 / 明線 / 汀の魚） | しない |
| `hp`  | 幾何でないもの（沈み込み / 計器の不透明度 / 時間の倍率） | 0.09秒 |

幾何を平滑化しないので、どんなスクロール速度でも線がずれない。

- 汀の窓 `cEff()` … `hpR` 0.36〜0.60 の間だけ、シートの**見かけの**上端を
  実スクロールの6%しか動かさない（`SEAM_K`）。実スクロールは1pxも奪わない。
  画面を約100px送るあいだ2本の線は4px以内に収まる。
  **6%を0%にしてはいけない** ―― 完全に止めるとスクロールの乗っ取りに読まれる。
- 窓は前後で非対称（下 0.14 / 上 0.10）。上側を 0.60 で閉じ切るのが要で、
  描画が止まる 0.62 で窓が開いたままだと、本文が数pxずれた位置で固まって戻らない。
- `measureSeam()` は **必ず `rect.top - seamDelta`** で測る。自分が当てている
  transform を引かないと、rect → hpR → seamDelta → rect の自己参照で発振する。
- `hpR ≥ 0.62` で `renderSettledFrame()` が**記録の1枚**を1回だけ描く。
  フリックで飛んだ人もゆっくり降りた人も、この1枚は同じ絵になる。
  実績の3件目のタイルへ写すのがこの1枚（`captureLiveShot()`）。
- **そのあと海は止めない。「凪」で回す。**
  以前は本文へ渡った時点で描画を完全に切っていた（FPSと電池のため）。
  ただ海が主役のサイトで、読んでいるあいだだけ海が死んでいた。

### 凪（読書中の描画）

| | 値 | なぜ |
|---|---|---|
| `READ_CALM` | `0.28` | 時間の底。600mの海はゆっくり動く |
| `READ_FPS` | 30（低ティア24） | 描く回数だけ間引く。`t` は毎フレーム進めるので**速さは実時間どおり** |
| 被写界深度 | 切る | 62%の地の裏では見えない |
| 散乱のサンプル | 26/12 → 8 | 同上 |
| ブルーム | 半解像度 | 同上 |
| 水面の映り込み | 切る | 600mでは画角に入らない |
| カメラ | 据える | ポインタで視点が動くと文字の裏の絵が一緒に動いて読みにくい |

- 止めるのは **`prefers-reduced-motion` と `saveData` だけ**。
  **端末で差を付けない**（デスクトップだけ動く、は要綱で禁止）。
  落とすのは描く頻度と重いパスであって、動きそのものではない。
- **`setReadingQuality()` と品質の梯子（`setQuality()`）を同時に走らせない。**
  描く回数を間引くと1フレームの平均が実力より速く出て、梯子が勝手に登り、
  `LADDER.up()` が読書用に落としたパスを戻してしまう。凪のあいだ梯子は据え置き。
- **DPRは触らない。** 変えると canvas が張り直されて記録の1枚が消え、
  resize 経路（`measureLayout()` / `resetFishState()`）まで走る。
- 実測（3時点・両ビューポート）: 文字のコントラストは最小 **11.41:1**。
  reduced-motion は水面・汀とも**差分0画素**のまま。
- 本文の最後 `#outroOpen`（58vh）に入ると `rp` が立ち、**海が戻る**。
  `t` は1秒も進んでいないので、集光も魚も止めた場所から続く。

計器は消えず、**測る対象が深度から読了へ替わる**。
`#foot` は全画面幅で担い、`#ruler` は 1240px 以上でだけ目次になる
（それ未満は本文カラムと重なるので退役する。閾値は実測で決めた）。

## 魚 — 「間合い」

姿ではなく間合いを描く。**居場所はワールドに置き、カメラがその中を通り抜ける。**
群れをカメラの周りに置くと常に5m以上離れたままになり、警戒の半径（2.3m）に
一度も入らないので「反応」が一度も起きない（最初そう書いて、起きなかった）。

- 画面の中央に来るほど薄れる（周辺視）。床0.22・鈍り0.6秒は交渉不可。
- 逃げるときは半径方向ではなく**横**へ抜ける。必ず画面の端から出る。
- 刺激は距離ではなく**近づかれ方**（速さ `rush` / 正対 `look`）。
  ゆっくり降りた人の前では散らない。
- **止まると寄る。** ゲート3つ（カードを読んでいない / 汀の手前でない /
  スクロールが止まっている）は全部必須。
- 深いほどこちらを無視する。600m先で最も近くを通る1匹はこちらを見ない。
- `uFishWake` … マリンスノーを押しのける。**品質の梯子で切らない。**
  姿が見えなくても雪が割れれば「居る」と分かる、明るさに依存しない唯一の手段。
- 品質の梯子で落とすのは **近寄る距離だけ**。数も振る舞いも減らさない。
- 乱数は固定の種（`?fishSeed=` で上書き）。撮影と回帰が毎回同じ絵になる。
- `aPhase` は CPU で進め、必ず `timeScale` を掛ける。掛け忘れると
  凍った海の中で尾だけが振れ続け、「止まっている＝記録」が無効になる。

### 泳ぎ方（動きと姿勢）

- **体を走るうねり。** `sin(aPhase)` だけだと体の全部が同じ位相で同時に曲がる
  ——「しなる」ではなく「折れる」。位相を `uvv.x` ぶん遅らせて波を頭から尾へ
  走らせる（2.6rad ≒ 体長の0.4波長。アジ型）。頭は反作用で逆へ12%振れる。
- **上下に泳ぐ意志。** `fDir` は x,z しか持たない。周期の違う2つの波で
  「降りている魚」と「昇っている魚」を混ぜる。これが無いと全部が同じ水平面を滑る。
- **バンク。** ヨーの変化率から曲がる側へ倒す。**角度差は必ず ±π へ畳む**
  ——畳まないと `-179°→179°` の1フレームで「358°回った」ことになり体が裏返る。
  **上限24度。** 板は平面なので、これ以上倒すと「バンクする魚」ではなく
  「回転する切り抜き」に見える。
- **ロールは体の前後軸、ピッチは体の左右軸まわり。** ワールドXYZで回すと
  ヨー90度のときに上下と左右が入れ替わる。ヨーの後に掛けてローカル軸で回す。
- **振り幅は上限を超えさせない。** 周期（`fBeat`）は元から速度連動。振り幅を
  速度で「増やす」向きにすると元の上限 0.028 を25%超えて体が折れた（実測0.0333）。
  速さが効くのは「遅いときに振らない」方向だけ。
- 汀の一匹と湧き直しでは**姿勢を必ず戻す**（前の個体の傾きを引き継いで現れる）。

**残っている限界: 板は平面なので、体の軸が視線と重なると幾何学的に線になる。**
実測で可視の魚の **8.3%** が真正面±15度に入る。完全に直すには体の断面を向いた
3枚目の面が要る（体の軸を含む2枚を十字に組んでも、正面から見れば両方とも線に
なるので効かない）。いまは線になる手前で薄れさせて「向こうを向いた魚が
見えにくくなる」に読み替えてある。`scratch/viewangle.mjs` で頻度を測れる。

### 姿の描き方（3回踏んだので明文化する）

板は `PlaneGeometry(0.42, 0.20)`＝**2.1:1**。ここが全部の罠の元。

1. **形は uv ではなく「実寸の比」で書く。**
   `X = uv.x` / `Y = (uv.y - 0.5) * 0.4762`。両方「体長を1」とした同じ尺なので
   `length()` がそのまま円になる。uv.y をそのまま高さに使うと縦が 2.1 倍に
   潰れ、狙った 2:1 の胴が **4.3:1 の棒**になる。ぼかしが乗ると完全にただの線。
2. **胴と尾は必ず重ねる。** 尾柄（0.70〜0.80）に細い下限を残す。
   ここが 0 まで落ちると胴と尾が切り離れ、「魚1匹」ではなく「塊2つ」に見える。
3. **尾の外形を `tv*tv` で開かない。** 鰭が軸に貼りついたまま先端だけ広がり、
   上下の葉が細い筋になって燕の尾になる。`pow(tv, 0.8)` で早めに開かせる。
4. **陰影は「上下に1本グラデーション」にしない。** それだと塗り分けにしか
   見えない。水中の光は上から来る。逆行迷彩の魚は「背＝暗い色素・よく当たる」
   「腹＝明るい色素・当たらない」で、掛け合わせるといちばん明るいのは
   腹の縁でも背でもなく **体側の帯** になる。そこが本物の顔。
   色素の切り替わりを急にすると背が黒に潰れ、明暗の境目が硬い線になる。
   暗い側も 0 まで落とさない（落とすと逆行迷彩ではなく影になる）。
   側線・鰓蓋・鱗の3つは、小さくても脳が魚と判定する手がかり。
   眼は虹彩・瞳・ハイライトの3つ。黒い点1つだと漫画になる。
5. **`depthWrite:false` にしない。** 被写界深度は深度バッファを読むので、
   深度を書かない魚の画素では「魚の**奥**にある景色」のボケ量が当たる。
   汀の魚はカメラの手前 5〜8m に居るのに背後の砂（30m超）のボケが乗り、
   何をしても永久にぼやけたままになる。形は `discard` で抜いているので
   深度を書いても輪郭は濁らず、ついでに魚どうしの前後と、光条に対する
   シルエットも正しくなる。
6. **板に横分割を入れる。** 四隅4頂点だと頂点シェーダの
   `smoothstep(0.15, 1.0, uv.x)` が 0 と 1 でしか評価されず、曲線が消えて
   平行四辺形に傾くだけになる（＝「泳ぐ」ではなく「傾く」）。横10分割で胴がしなる。

## 海 — 「リアルさが足りない」の内訳

「海が嘘くさい」は主観に見えるが、撮って画素を測ると毎回はっきりした
原因が1つずつ出てくる。撮る道具は `scripts/sea-shots.mjs`（潜航の 0 / 0.06 /
0.14 / 0.30 の4点で、本文とHUDを消して撮る）、測る道具は
`scripts/sea-profile.mjs`（縦の輝度・彩度プロファイル）。
**絵を見て「なんとなく」直さない。** 直す前と後で必ず数字を並べる。
逆に、**目で見えた「段差」も測ってから直す** —— 水平線の継ぎ目が硬く
見えたので測ったら、1行あたりの最大段差は 1.1 しかなかった（＝段差では
なく、細波の有無という質感の変わり目を輪郭として読んでいただけ）。
手前の浮遊物の「四角い縁」も同様で、実測は 4px で 5 階調の傾斜だった。

これまでに見つかって直したもの:

1. **遠景が定数1色だった。** `mix(col, uFog, farFade(d))` の `uFog` が
   スカラー1色なので、38m より先は画面のどこでも同じ画素値になる。
   実測で **画面 180px にわたり rgb(24,91,104) が1も動かなかった**。
   水ではなく「水色の霧の板」に見える。
   → `G_FAR` の `fogAt(fog, V, S, depth01)` を作り、**位置ではなく視線の
   向きだけの関数**にした。向きの関数である限り、空ドーム・水面の裏・
   魚・カード・海底が同じ画素では必ず同じ壁を見るので、継ぎ目が出ない
   （定数だったのはそのためで、勾配を付けても安全なのはこの性質による）。
   `mix(col, uFog, …)` は**もう書かない**。必ず `fogAt()` を通す。
   - 色を動かしすぎない。下向きで赤を落とすのは物理どおりだが、赤を
     0.62 倍にしたら **彩度 77% → 99%** に張り付き、海水ではなく
     プールの水になった。上下の色差は1割強までに留める。奥行きは
     明暗（0.52〜1.20）でほぼ全部出る。

2. **天井のきらめきが常時飽和していた。**
   `clamp(length(g)*6.0, 0.0, 1.0)` は、近景で `length(g)` が 0.8 まで出る
   ので上限に張り付きっぱなしになる。飽和し切らなかったわずかな谷だけが
   残り、天井が**ミミズ状の落書き**に見えた。
   → 飽和させず `smoothstep(0.04, 0.58, length(g))`。あわせて全反射側
   （`tir`）では消す —— 光が入るのはスネルの窓の側だけで、鏡の側が
   煌めくのは物理的におかしい。

3. **放射メッシュのリングが平行な細線になった。**
   水面のすぐ下から浅い角度で見上げると、リング間の線形補間がそのまま
   「櫛で梳いたような細線」として天井に出る。細波（`g`）が
   `exp(-d*0.055)` で 20m 先には 1/3 まで落ちており、**縞を割るものが
   何も残っていない**のが原因。
   → (a) 天井では細波を**波長ごとに**落とす（`rippleD()`）。
   (b) 浅い角度＋距離で頂点法線を捨て、陰影を細波だけで作る（`nflat`）。

   ここで一度**踏んだ**: 減衰を全項まとめて緩めた上で高周波を2本足したら、
   1画素を切った波が残って**籠の網目のようなモアレ**になった。画面での
   大きさは `1/(距離×周波数)` なので、**減衰も距離×周波数で決める**。
   `exp(-dist * fr * 0.0090)`。短い波は自分で先に消える。

4. **「降下の背骨」を置くのをやめた。** 深さの基準として細い円柱を1本
   立てていたが、実測すると画面を縦断する**マットな灰色の直線**として
   出ていた。外洋の水中に支柱が浮いている絵は現実に無く、写真らしさを
   最も強く壊していた。深さの手掛かりは HUD の計器・光芒・マリンスノーの
   視差で足りている。

5. **浅いところで光芒が一切立たなかった。** ゲートが
   `smoothstep(0.02, 0.30, uDepth)` で、潜り始めの水が「色の付いた板」に
   なっていた。実際の海は水面直下がいちばん光条が強い。
   → `smoothstep(0.012, 0.19, uDepth)`。

6. **光芒が鉛直に立っていた＝舞台のスポットライトだった。**
   夕景の太陽は水平から 4.9度（`SUN.y = 0.085`）しかないので、入射角は
   鉛直から 85.1度。スネルの法則で `sin(85.1°)/1.333 = 0.747` →
   **屈折角は鉛直から 48.4度**。水中の光条は真下ではなく、太陽の反対側へ
   大きく傾いて差す。
   → `RAY_DIR` を1回だけ求め、板の軸を `RAY_UP` に取ってその軸まわりで
   カメラへ向ける（`makeBasis` → `setFromRotationMatrix`）。
   板の中点の高さは変えていないので、上端は水面直下・下端は海底のまま
   ずれるのは xz だけ。丈は `SHAFT_LEN = (SEABED_Y + 0.30) / RAY_DIR.y`。
   - **画面で放射状に開くのは透視のせい**なので、以前あった z 回転の
     ごまかし（太陽の画面座標からの `lean`）は消す。水中の光条は平行。
   - 着地の光だまり（`uShaft`）は**下端の xz**を渡す。中点のままだと
     光条と光だまりが 5m 以上ずれて別物に見える。
   - 傾けると下端が 4.9m カメラ側へ来る。クラスタの z を奥へ下げ、
     `near` の消し始めも早めないと、手前の板が additive で白く飛ぶ。
   - **スクリーン空間の散乱（`uSunUV`）も同じ向きへ寄せる。**
     水中では太陽そのものではなく `RAY_UP` の無限遠が中心。ここを
     太陽のままにすると、画面の筋と板の向きが食い違う。

7. **周波数の近い正弦を2本並べない。** 天井の細かさを足すのに 38 と 61 の
   正弦を並べたら、干渉して**菱形のうなり（モアレ）**が出た。1本は正弦、
   もう1本はノイズの勾配にして、うなりの相手を作らない。

## iPhone の実寸で見る — px と vh を混ぜない

**利用者の実機は iPhone 14。** Safari は URL バーのぶん見える高さが画面サイズより
ずっと短く、**390×664**（バー表示時）/ **390×750**（縮んだ後）。
`390×844` は「画面サイズ」であって Safari の表示領域ではない。
ここを取り違えて 844 の絵ばかり見ていたせいで、下の崩れを長く見落とした。

### 見つけた崩れ
| | SE 553 | mini 629 | 14 664 | 844 |
|---|---|---|---|---|
| 見出しが DEPTH に被る | **24px** | **9px** | **2px** | 0 |
| カードが下HUDに被る | **13px** | 0 | 0 | 0 |

原因は **`#meter` が `top:88px` の固定px（下端は常に 135px）なのに、`#hero` が
`top:20vh`** だったこと。画面が低いほど vh が縮んで meter に潜り込む。
→ `top:max(20vh, 153px)`。**px と vh を混ぜたら、必ず `max()` でどちらが勝つか決める。**

### カードは上端だけでなく下端も見る
`solvePortraitLift()` は長らく「カードの上端が文字より下」だけを保証していた。
下端は誰も見ていないので、画面が低いとカードが下のHUDに潜り込む。
文字とHUDに挟まれた帯に収まる倍率まで縮める。**そのとき2つ間違えた**:
1. **投影を自前で解き直した** → 実際に描かれる 112px に対して 165px と答え、
   必要の倍以上に縮めた（画面幅の21%まで）。面のヨーとゆらぎが乗るので素の
   高さからの計算とは合わない。**`cardScreenRects()` の実測をそのまま使う。**
2. **「いまの倍率」に係数を掛けた** → resize やフォント読込でこの関数は複数回
   走るので掛け算が積もる（0.86 → 0.5375 → 0.3634）。**必ず元の倍率を起点に**。

### 背の低い縦画面では文章を削らず、縦のリズムを詰める
「ホームページをつくっています。福岡・北九州から。」はこのサイトが何屋かを言う
唯一の行で、いちばん狭い画面でこそ要る。`@media (max-height:640px)` で
DEPTH の計器を上げ、行間と余白だけ詰めて場所を返す。
結果のカード幅: SE 49.6% / mini 55.5% / **iPhone14 57.4%** / 844 70.3%。

### 知らない `--view` を desktop に落とさない
`probe.mjs` と `verify.mjs` は**別々のビューポート表**を持っていて、片方にしか
無い名前を渡すと黙って 1600×900 を測っていた。実際に2回やられ、
「iPhone の結果」として読んだ数字が desktop のものだった。
→ 未知の名前は即 `exit 2`。**黙って別のものを測るくらいなら止まる。**

## 作品カードは「無色のガラス板」— 中身は透かさない

**透かすのは板であって、作品の絵ではない。** ここは2回まちがえた。

1回目は「ガラスに見えないのは絵が不透明だからだ」と考えて、絵の輝度で
透け方を変えた（暗い所ほど透ける）。実際にはそこは問題ではなく、
**板が青緑の色ガラスだった**ことが原因だった。絵を透かすと、今度は
実績が何のサイトか判らなくなる。

### 直したのは板の色
```
// 旧: 青緑を55%掛けたうえ、明るさも 0.86〜0.68 まで落としていた
vec3 tint = mix(vec3(1.0), vec3(0.62,0.86,0.92), 0.55);
vec3 col  = bg * tint * (0.86 - bevAmt * 0.18) + glass;
// 現: ほぼ無色。景色をそのまま通し、わずかに減光するだけ
vec3 tint = mix(vec3(1.0), vec3(0.93,0.97,0.99), 0.55);
vec3 col  = bg * tint * (0.97 - bevAmt * 0.10) + glass;
```
斜めから見た時の白み（`glass +=`）からも色を抜いた。ここに青緑を盛ると、
**透かした景色まで染まって色ガラスになる**。無色の板は、映り込みと縁の
ハイライトだけで存在を示す。屈折・色収差・小口の全反射はそのまま効いている
ので、「opacity を下げただけ」には見えない。

作品の絵は `content.a` でそのまま乗せる。**板は透明でも中身は透かさない。**

### それでも青かった — 空気中の板に水の霧を掛けていた
色ガラスを抜いてもまだ青く見える、と指摘された。**測って**原因が出た。

| | rgb | 彩度 | 青−赤 |
|---|---|---|---|
| 板の外 | (44,50,54) | 10% 前後 | +1〜+13 |
| 板の内 | (65,86,82) | **21〜30%** | +16〜+26 |

同じ景色が板の縁をまたぐ所で測ったので、この差は**板が足した色**。
犯人はガラスの色ではなく `waterFogV()` を**カメラも板も水面の上にいる時にも
掛けていた**こと。`ABSORB` は赤を最も吸う（0.115 / 0.032 / 0.018）ので、
6.7m ぶん掛かるだけで**赤が半分**になり、無色にしたはずの板が青緑に転ぶ。

```
float wet = 1.0 - smoothstep(-0.25, 0.45, min(cameraPosition.y, vW.y));
col = waterFogV(col, d * wet, ...);   // 水面の上なら距離0＝水は無い
```

修正後の実測: 板の内の彩度 **25% → 5%前後**、外と一致。水中（どちらかが
水面より下）は従来どおり霧が掛かる。

**教訓**: 「無色にしたのに色が付く」時は、材質ではなく**そこへ至る経路**を疑う。
そして目で見て決めない —— 縁をまたぐ1本の線を測れば10秒で判る。

## 底の造作（海藻と岩）

砂だけの平面は、どれだけ水を澄ませても「広い床」にしか見えない。大水槽らしさは
**縦の構造**と、そこに当たる光でできている。

- **配置はカメラの筒を避ける。** カメラは x∈±0.30 / z∈±0.10 の細い筒を降りるだけ
  なので、半径 3.2m より外なら絶対にぶつからない。
- **時計は水と共有する。** 海藻は水面と同じ `T` で揺れる。別の時計にすると
  「水が凪いでいるのに海藻だけ動く」が起きる（読書中の凪もこれで一緒に効く）。
- **発光させない。** 暗い影として立たせて、光条と集光で浮かせる。

### 4回作り直した。毎回ちがう理由で嘘に見えた
1. **幅 0.20 → ストローに見えた。** 海藻は幅のある葉。0.34 へ広げ、分割も 8→12。
2. **全部まっすぐ立った → 造花に見えた。** 揺れだけを入れると、位相がたまたま 0 に
   近い株が定規のように直立する。**株ごとの「くせ」（静止時の曲がり）を常に持たせる。**
3. **色が鮮やかすぎた。** `(0.075,0.130,0.078)` は青い水の中で緑が浮く。褐藻寄りの
   くすんだ色へ。さらに**幅方向の丸み**（中央が明るく縁が落ちる）を入れる ——
   これが無いと、形を整えても「平らな厚紙を立てた」ようにしか見えない。
4. **先端が平らに切れていた。** 頂点側で幅を絞っても `uv.y=1` は断面として残り、
   「切ったパイプ」に見える。**葉の幅そのものを高さの関数**にして、先で 0 にする。

### 岩
最初の albedo は最大 0.062 で、砂（最大 0.098）の6割しかなく、光の当たった砂の上で
**黒い影の塊**に見えた。岩は砂よりやや暗い程度が正しい。`IcosahedronGeometry` の
detail も 1（80面）だと角張って「破片」になるので 2（320面）へ。半分は砂に埋める
（全部載せると置いただけの小道具に見える）。

### 散らす範囲は「視程」で決める
最初 26m まで散らしたら、大半が霧の中で消えて画面には2株しか出なかった。
計器の `VIS`（51〜89M）ではなく**実際に見える範囲**、つまり 15m 程度へ寄せる。

## 急速潜航

速く巻いた時だけ入る状態。**しきい値・時定数・画角はすべて `RAPID_*` 定数1箇所**
（`index.html` の `scrollVel` 宣言直下）に集約してある。調整はそこだけ触る。

| 定数 | 初期値 | 意味 |
|---|---|---|
| `RAPID_ON` | **0.55** | `\|scrollVel\|` がこれを超えたら発動 |
| `RAPID_OFF` | **0.32** | これを下回ったら解除 |
| `RAPID_RISE` | 0.18s | 立ち上がり |
| `RAPID_FALL` | 0.75s | 戻り（仕様 0.5〜1.0 の中央） |
| `RAPID_FOV` | +12° | 最大で足す画角（仕様 +10〜15） |

`scrollVel` は「1秒で潜航のどれだけを進むか」。**0.55 は「2秒弱で潜航を通過する
勢い」**にあたる。読む速さのスクロールでは出ず、意図的に速く弾いた時だけ入る。
出やすくしたいなら `RAPID_ON` を下げる。

### ヒステリシスは必須
発動と解除を同じ値にすると、その付近でスクロールが揺れるたびに ON/OFF が
往復し、画角と色収差がバタつく。実測: 0.56 で ON、下げても **0.34 では ON のまま**、
0.30 で OFF。単一しきい値なら 0.55 未満で切れていた。

### 一次遅れで戻してはいけない
最初 `rapid += (target-rapid)*dt/RAPID_FALL` と書いた。一次遅れは目標へ
**漸近するだけで到達しない**ので、実測で 0.715 から30フレーム経っても **0.09 が残り、
画角が基準へ戻らなかった**。画角は汀線の幾何（`horizonPx` は fov に依存）に効くので、
これは見た目以上に悪い。→ **一定速度で詰める**（`rapid ± dt/RAPID_*`）。
1→0 がちょうど `RAPID_FALL` 秒で、確実に 0 に触れる。
このリポジトリで同じ罠は RATE でも踏んでいる。

### 色収差はパスを足していない
GRADE（最終パス）に**既に色収差が入っており**、3タップ取っている。係数を
上げるだけなので**追加コストは 0**。新しいフルスクリーンパスは足していない。

### 泡
`InstancedMesh` 1つ、**追加ドローコールは +1**。位置は「種 + 時刻」から頂点シェーダで
解くので、CPU の毎フレーム処理は uniform 3本だけ。板はビュー空間で組む
（スクリーンに正対、流れる向きは画面の縦）。`rapid` が 0 の間は `visible = false`。

### ティアごと
| | 泡 | 色収差 | 画角 |
|---|---|---|---|
| high | 320 | ON | 56 → 68 |
| low | **160**（半減） | **OFF** | 64 → 76 |
| reduced-motion | 全効果 0 | | |

### 低フレームの端末では発動しない（設計上の安全弁）
上流に `if (rawDt > 0.08){ velX = 0; velV = 0; }` があり、**12.5fps を下回るフレームは
速度入力ごと捨てられる**。つまり既に重い端末では急速潜航に入らない。
（開発環境が約0.6fps なのはこのためで、**ここでは実スクロールで発動を観測できない**。
`__diag.rapidForce` に強度を注入して検証する。）

### 60fps の確認は端末に測らせる
この環境は SwiftShader で 0.5〜0.7fps なので**「60fps維持」はここでは測れない**。
相対コストは全開で **1.23〜1.28倍**（大半は画角を開いたぶんの描画面積で、
CPUラスタライズではとくに高く出る）。実機は `?bench=1` の
**「急速潜航」の行**で測れる（計測中に強度を注入して、その区間のフレーム時間を採る。
実際に速く巻かせると端末の速さで発動したりしなかったりして比較にならないため）。

## クジラ — 280〜380m で、1セッションに1度だけ

潜航の途中で巨体が奥を横切る。**1セッション1回**（`whaleDone`）で、
戻って再侵入しても二度と出さない。珍しいから効くのであって、往復するたびに
出たらただの装飾になる。定数は `WH_*` 1箇所（`index.html` の 4.7節）。

| 定数 | 値 | 意味 |
|---|---|---|
| `WH_BAND` | **[280, 380]** | この帯に初めて入ったら発火（m） |
| `WH_DUR` | **12.5s** | 通過にかける秒（仕様 10〜15 の中央） |
| `WH_LEN_SCR` | **1.15** | 最接近時に画面幅の何倍に見せるか |
| `WH_LEN_CLAMP` | [5, 21] | 体長の上下限（世界単位） |
| `WH_Z_FAR` / `WH_Z_NEAR` | 21 / 12 | 出入りの奥行き / 最接近の奥行き |
| `WH_FADE` | [0.06, 0.16] | 出入りのフェード（進捗 0..1 で） |
| `WH_SONAR_M` | 4.2 | 世界単位 → ソナー表示のメートル |

### 発火は `depthShown`（着底と同じ）
計器が「310.4M」と出ているのに接触表示だけ先に走る、を避ける。
`qStep >= 3`（品質梯子が3段落ちた＝既に重い端末）と reduced-motion では
**そもそも武装しない**。

### 大きさは画角から逆算する
固定の体長にしてはいけない。この世界は横長（fov56 / 16:9 → **水平86°**）と
縦長（fov64 / 9:19.5 → **水平40°**）で水平画角が倍以上違う。固定にすると
スマホで小魚、PCで画面外になる。`whaleSize()` が
「最接近 `WH_Z_NEAR` で画面幅の `WH_LEN_SCR` 倍」を解く。

**仕様の 1.5 倍からは落としてある。** 1.5 で出したら画面の6割を占める
黒い塊になり、形として読めなくなった（実測）。「輪郭は霧に溶かす」とも
噛み合わない —— `farFade` は16m以遠なので、近すぎて溶ける距離に入らない。
1.15 ＋ 最接近12単位が、画面より大きい手応えを保ったまま形が読める境目。

**縦画面はさらに 0.82 に落とす。** 同じ「画面幅の1.15倍」でも、
縦長の窓では細長い体の胴だけが残って**ただの黒い帯**になった（実測）。
狭い画面ほど全身が入るようにしてある —— PCだけ良く見える、の逆。
下限は 5.0。7.0 のままだと縦画面が下限に貼り付いて 0.82 が効かない
（実測: 5.68 が 7.0 に押し戻された）。

### 置く場所は「世界のy」ではなく「カメラの基底」
この帯ではカメラが **+8.6° 上を向いている**（`camera.rotation.x` は
`sp` で動く）。`camera.position.y + 1.15` に置いたら画面の下の外へ落ちた。
→ `whaleAt()` が前方・右方・上方の単位ベクトル（`camera.quaternion` から）で組む。
向きは「少し先の位置との差」をそのまま基底にする（斜めの分だけ自然に首が振れる）。
水面（0）と海底（-10.4）は `pad = 体長 × 0.11` で挟んでクランプする。

### 「巨大な木の葉」になった → 直したのは色と距離で、形ではなかった
1. **明るすぎた（これが本命）。** `waterFogV` に周囲と同じ `light = 1.0` を
   渡したら、内散乱で体が白茶けて**背景より明るい木の葉**になった。
   降ってくる光を遮っている巨体なので暗いのが正しい。→ `light = 0.34`。
2. **近すぎた。** 最接近 9.5 単位・画面幅の1.5倍では、胴の一部しか窓に
   入らず塊にしか見えない。12 単位・1.15 倍にして全身を入れたら読めた。

**半径の式をいじったら悪化した（戻した）。** 「頭は 0.13 で太さに達し
0.26 から絞り続ける」細い式に変えたら、胴が薄い板になって鰭だけが目立つ
**艦船**になった（実測）。元の太めの式が正しい。

**教訓**: シルエットが読めない時、最初に疑うのは形ではなく**輝度差と距離**。
形をいじるのは最後にする。

### 鰭は「板」で生やすと必ずスラブになる（3回踏んだ）
背びれを独立した三角として立てると、なめらかな胴の上に**平たいスラブが
1枚浮いて**見える。大きさを変えても直らない —— 面積を持った平板が
曲面の上に乗っていること自体が読まれる。

→ **胴の面そのものを盛り上げる。** 断面を回すループの中で

```js
const fin = 0.028 * Math.exp(-Math.pow((u - 0.70) / 0.105, 2))
                  * Math.pow(Math.max(0, sy), 3);
pos.push(0.57 - u, sy * rr * 0.90 + fin, cz * rr * 1.04 * lat);
```

`sy^3` を掛けているので持ち上がるのは背の頂点だけ、釣鐘なので稜が尖らない。
（三角のテントで盛った版は**鮫の背びれ**になった。ナガスクジラの背びれは
低くてなだらか。）

胸びれだけは面を持たせるしかないが、**三角1枚を胴に沿わせる**に留める。
4角に広げて腹の下まで垂らしたら、やはり胴から離れた板になった。

### 「クジラ感」を決めているのは頭
胴と尾びれだけを整えても、頭が**円錐で終わっている**とイルカにも潜水艦にも
見える。横顔のクジラをクジラにしているのは、次の3つの組み合わせ。

| | 実装 |
|---|---|
| **深い下顎** | 下側だけ `u = 0.02〜0.32` でふくらませる（最大 0.13）。`0.030 * exp(-((u-0.13)/0.115)²) * max(0,-sy)^1.4` |
| **平らな吻** | 頭の上面はほぼ直線。`1 - 0.22 * max(0, 1-u/0.26) * max(0,sy)` を半径に掛ける |
| **口の線** | 顎の高さ（断面上の `sy ≈ -0.22`）の帯を 0.34 だけ暗くする。頭の範囲（`vU < 0.34`）だけ |

口の線は**模様ではなく「顎の合わせ目」**。これが1本入るだけで、同じ
シルエットが「魚っぽい何か」から「クジラ」に変わる。

**断面上の高さは `uv.y` から戻してはいけない。** `j = RING-1 → 0` の継ぎ目で
値が 0.93 → 0 と飛び、そこだけ帯が崩れる。`aSy` 属性で渡す（sin は
リングを一周しても連続）。

**尾柄を絞りすぎると「エイ」になる。** 0.55 まで細くしたら、細い棒の先に
幅広の板が付いた形に見えた（実測）。尾柄は細いが、胴から連続して見える
太さは要る → 0.34。尾びれの幅も 0.300 → 0.262 に戻した。

### 形で効いたもの（順に）
1. **断面を真円にしない** —— 背を 0.90倍に絞り、腹を 1.13倍にふくらませる。
   真円だと「空気で膨らませた筒」に見える。
2. **尾柄の側扁** —— `u > 0.70` で左右を最大 0.45倍まで薄くする。
   ここが丸いままだと尾びれが「棒に刺さった板」になる。
3. **尾びれを三日月に** —— 後縁が凹んで中央に切れ込みのある形。
   扇（三角2枚）から 6枚へ。クジラの尾を尾らしくしているのは後縁の凹み。
4. **断面 8角 → 14角 / 輪切り 14 → 20** —— 背中の稜のカクつきが消える。
   570三角形になったが、描画コストは測定の揺れに埋もれた。
5. **背の稜に光を1本** ——
   `smoothstep(0.42, 0.92, N.y) * pow(1 - |dot(N,V)|, 1.8)`。
   上を向いていて視線から逃げる面＝輪郭の上側。**面では光らせない。**
   これが無いと、どれだけ形を作っても「切り紙」から抜けない。
6. **体全体の反り** —— 尾だけ振ると「棒の先がしなっている」に見える。
   `sin(ph*0.62) * 0.017 * (0.32 + 0.68*uv.x)` を全体に掛ける。
   頭も少しだけ動くのが、生き物と潜水艦の分かれ目。
7. **輪郭のきわを 0.86 まで透かす** —— 硬いまま切ると「型紙」に見える。
8. **逆行迷彩** —— 「上ほど明るい」単純なグラデーションだと、丸みが出ず
   平たい紙に見える。魚と同じ考え方に揃えた: **背は暗い色素でよく光が当たり、
   腹は明るい色素で光が当たらない**。掛け合わせた結果いちばん明るくなるのは
   **体側**で、そこが本物の顔。これで初めて胴が「丸い」と読める。
9. **光芒を海底と共有する** —— `uShaft` / `uShaftN` / `uPulse` は
   **海底のユニフォーム実体をそのまま渡している**。別に作ると
   「砂の上を走っている光の柱」と「クジラに当たっている光」が別物になる。
   同じ光の柱の中を通らせて、上向きの面だけを持ち上げる。
   これが入ると、クジラが**シーンの中に居る**ようになる。
10. **喉の畝** —— ナガスクジラの喉には縦の溝が並ぶ。9%だけ暗くする。
   `asin` で断面の角へ戻すと溝が腹まわりに等間隔で並ぶ。
   これ以上やると「柄のついた魚」になる。

### 板（低ティア）は**外した** —— スマホがいちばん悪い絵を見ていた

「出たけどショボい」と言われて実機の経路を見たら、**スマホは板版**だった。
板は進路がカメラ側へ振れた瞬間に潰れるので、**入り際・出際が
ただの黒い楕円**になる（実測 `wh7-low-2_6.png`）。いちばん見せたい
「奥から現れる」場面が、いちばんひどかった。

そもそも **568三角形・ドローコール1本はスマホには何でもない量**で、
効くのは塗り面積とフルスクリーンパスの方 —— それはメッシュでも板でも同じ
（同じシルエットを塗る）。**ティアで分ける理由が最初から無かった。**
計測せずに用心しただけだった。

→ 板を丸ごと削除し、全ティアでメッシュ。品質梯子の門も `qStep < 3` から
`< 5` へ緩めた（落とすべきなのはフルスクリーンパスの方）。
以下は削除した板版のための記述だが、**「ティアで見え方を揃える」という
苦労そのものが、分けたことの代償だった**ので記録として残す。

### （旧）板はメッシュの見え方に合わせる必要があった
輪郭式は共通だが、**見え方まで合わせないと別の生き物になる**。
- 尾びれ: メッシュは水平なので真横からはほとんど厚みの無い刃。板側で
  厚く描いたら、体高の7割まで開いて**魚の尾に戻っていた**（実測）。
  メッシュの先端が軸から 0.042 しか上がらないのに合わせる。
- 背びれ: 同じ釣鐘の式で背の輪郭を持ち上げる。
- 背の稜: 板に法線は無いので、**マスクを1回だけ上へずらして引き算**して
  「上の縁」を取る（`m - texture(uMask, vUv + vec2(0, 0.010)).r`）。
  テクスチャ読みが1回増えるだけ。これが無いと低ティアだけ真っ黒になる。
- 逆行迷彩と光芒: 法線が無いので、**板の中の高さから代わりの `ny` を作る**
  （胴は `vUv.y = 0.21〜0.67` に入る）。色素も光芒もメッシュと同じ式。

### 前後の向き
機首を **+X** に向けて組んである（進行方向へ向けるとき基底をそのまま作れる）。
低ティアの板も**マスクの機首を右に描く**。片方だけ直すと、
ティアによって前後が逆のクジラになる。

### 面と深度
閉じた体なので `FrontSide` + `depthWrite: true`。`DoubleSide` だと裏面が
手前に出て体の中が透ける。深度を書くので作品カードや海底との前後も正しく決まる
（魚も同じ理由で書いている）。

### `uFog` を二重宣言してシェーダを落とした
`G_WATER` が `uniform vec3 uFog;` を宣言している。材質側でもう一度書くと
コンパイルに落ちる（落とした）。砂煙の材質が `uSun` だけ宣言しているのはこのため。

### ソナーの距離は専用の尺
深度の尺（69.8m/単位）で出すと、画面いっぱいのクジラに **628M** と表示されて
計器が嘘になる。深度の尺は「潜航の深さ」の尺であって物の大きさの尺ではない
（魚は 0.42単位＝その尺だと29m）。`WH_SONAR_M = 4.2` で読み、
通過に合わせて 087M → 049M → 089M と増減する。

### 一行は中央に置く
`#sim`（計器）の行にしたいところだが、**`#sim` は820px以下で `display:none`**。
そこへ入れるとスマホで一度も出ない。RAPID / TOUCHDOWN と同じ理由で
`#sonar` を中央に置き、見た目だけ計器に合わせている。

### ティアごと
| | 体 | 三角形 | ドローコール | 実測の相対コスト |
|---|---|---|---|---|
| high / low とも | ローポリのメッシュ | **596** | +1 | 測定不能 |
| 品質梯子が5段以上落ちた時 | 出さない | 0 | 0 | — |
| reduced-motion | 出さない | 0 | 0 | — |

相対コストは同じカメラで「出す/出さない」を10フレームずつ交互に測った比
（`scratch/whalecost.mjs`）。**1を下回っているのは測定の揺れ**である。
繰り返し測ると 0.884 / 0.993 / 0.996 と散らばり、**揺れは±12%まで開く**
（SwiftShader・1フレーム 1.4〜2.6秒）。

→ **この環境ではクジラのコストは測れない**、が正しい結論。「0.99倍だから
ほぼ0」と書くのは、揺れを測定値と読み違えている。言えるのは構造の方だけ:
**ドローコール +1 / 568三角形 / 新しいフルスクリーンパスなし /
生きているのは1セッションで12.5秒**。実機の数字が要るなら `?bench=1` を
使うこと。
新しいフルスクリーンパスは足していないし、生きているのは
1セッションで12.5秒だけ。

★ この計測はカメラが 246m（帯の外）で落ち着いた状態で採った。
`whaleForce` は帯の外でも描くので比較は成立するが、帯の中で撮った値ではない。

モデルファイルも画像ファイルも足していない（輪切りから組む）。

### 動きと、まわりとの関係
形と光を詰めたあと、まだ「レールの上の模型」に見えていた。残りは2つだった。

- **バンク。** 進路は奥行き方向へ弧を描いているのに、体を真っ直ぐ立てた
  ままだった。旋回の内側へ倒す（`0.07 * sin(q*2π) * whaleDir` ≒ ±4°、前半と
  後半で逆向き）。基底を作ったあとに前方軸まわりのクォータニオンを前掛けする。
  ★ 最初は 0.15(±8.6°) にしていたが、仕様書のリアリティ強化で ±3〜5° に
  絞った —— 大型鯨類のロールはもっと静かで、大きく倒すと「旋回する飛行機」になる。
- **魚が逃げる。** 既にある「間合い」の仕組み（`fStart` の驚き）を
  そのまま使う。**カメラの間合いとは別扱い**にした —— カメラは
  速さ・正対で警戒半径が変わるが、クジラは相手が大きすぎて、寄られたら
  無条件に退くのが正しい。半径は体長の 0.55倍（≒体の長さ）。
  逃げ方も「必ず横へ抜ける」ではなく、体から遠ざかる向き（巨体なので
  横も縦も無い）。

魚が散るのが入って初めて、クジラが**まわりに影響を持つ大きさ**に見える。

さらに3つ。

- **通過の「間」。** 等速で横切ると「通り過ぎた」で終わる。最接近の前後だけ
  遅くして、見送る間を作る。
  `e = q + 0.42 * sin(2πq) / 2π` —— 微分は `1 + 0.42*cos(2πq)` なので
  真ん中で 0.58倍、両端で 1.42倍。`e(0)=0 / e(1)=1` で単調（係数が1未満なら
  微分は常に正）。実測で最接近前後の距離が 87→75M / 55→52M と縮んだ。
- **浮遊物が押しのけられる。** 姿が大きいだけでは「そこに在る」だけで、
  まわりの水を動かして初めて「進んでいる」に見える。魚の押しのけと同じ作りで、
  `uWhalePos` / `uWhaleR` を粒子3層で共有し、体の中心から外向きに逃がす
  （巨体なので向きの細工は要らない）。`uWhaleR = 0` の間は分岐にすら入らない。
  ★ 押しのけは**水面クリップより前**に置くこと。後ろに置くと、押し出された
  粒が空へ出る。
- **ソナーの刻み。** 毎フレーム数字が変わると、ソナーではなく「速度計」に
  見える。**0.45秒ごとに1回だけ読み直し**、読み直した直後がいちばん明るい
  （`0.78 + 0.22*(1-frac)`）。計器は連続値ではなく「掃引のたびに更新される」もの。

### リアリティ強化 —— 仕様書への対応で入れたもの
仕様書【クジラのリアリティ強化】で追加・調整した点。大半（縦のうねり・
カウンターシェーディング・フレネルリム・フォグ統合・8〜12秒の横切り・
水の押しのけ）は既に上の作りで満たしていたので、差分は以下。

- **頭→尾の伝播と振幅 1:4。** うねりは尾びれだけでなく体全体を波が走る。
  `ph = uv.x * 2.30 - uTime * 1.16`（uv.x=0が頭）で位相を体軸に沿って遅らせ、
  振幅は `0.028 + 0.084 * uv.x²` —— 頭は小さく尾で最大、比はほぼ 1:4。
  1ストロークは 2π/1.16 ≒ **5.4秒**（仕様の4〜6秒）。
  **振りは `p.y`（上下）が主**で、`p.z`（左右）は振幅 0.18倍の二次成分だけ。
  鯨類の尾は水平尾びれ —— 左右に振ると魚になる（仕様の禁止事項）。
- **胸びれの二次モーション。** 体幹より遅い別位相
  （`sin(uTime*0.55 + sign(z)*1.7)`）でゆっくり羽ばたく。前方 60% にだけ
  効かせ、`aFin` と `|z|` でひれの先ほど大きく。体幹と同位相にすると
  「全部が1枚の布」に見える。
- **浮上・沈降。** 通過中に1回半だけ `sin(q*5.2) * 体長*0.02` で上下する。
  whaleAt は向きを「少し先との差分」から採るので、浮けば機首が上がり
  沈めば下がる —— 別々に作ると首と体が食い違う。水面と海底は
  体半径+尾の振れぶん（体長×0.11）でクランプ。
- **体表の微細ノイズ。** `vnoise(vW.xz*7.0 + …)` を ±5% だけ、
  **8m より近い時だけ**掛ける（16mで0へ）。遠距離はフォグ側の仕事で、
  遠くまでノイズを乗せるとシルエットが汚れる。ひれ（`aFin`）は除外
  —— 薄い板にノイズが乗ると縞に見える。

やらなかったこと: 尾びれの左右振り・2秒以下のストローク・フォグを無視した
くっきり登場（`WH_FADE` の出入りフェード＋距離フォグで「にじみ出る」は
既存のまま）。
`__diag.whaleForce = 6.25` で通過の経過秒を固定できる（この環境は約0.6fps なので、
自然な通過を待つと1枚撮るのに十数分かかる）。

## 着底 — 600m に着いた一拍

潜航の終端（`depthShown` が 600.0M に確定する瞬間）に一度だけ入る演出。
砂煙・サーチライト・見出しのフェード・`TOUCHDOWN — SEABED` の帯を、
**`TD_*` 定数1箇所**（`index.html` の 4.6 節の直前）で並べてある。

### タイムライン（t = 着底からの秒）

| t | 出来事 | 定数 |
|---|---|---|
| 0.00 | 砂煙が立つ / `TOUCHDOWN — SEABED` が出る | — |
| 0.20 → 0.70 | サーチライトが立ち上がる（ゆっくり揺れる） | `TD_LIGHT_IN` |
| 0.55 → 1.30 | 見出し `#landing` がフェードイン（ライトに同期。CSS側 `.75s`） | `TD_HEAD_AT` |
| 1.70 → 2.20 | `TOUCHDOWN — SEABED` が消える（一拍だけ） | `TD_TAG_OUT` |
| 0.00 → 6.50 | 砂煙が広がって薄れる（仕様の 5〜8s の中央） | `TD_DUST_END` |
| 5.50 → 7.50 | ライトが落ちる | `TD_LIGHT_OUT` |
| 8.00 | `touchT` が -1 に戻り、板もコーンも `visible = false` | — |

再武装は `TD_REARM_M`（25m）。**600m から 25m 浮上して初めて次の到達を数える**。
着底点で±数十cm揺れるたびに撃ち直すのを防ぐため。2回目以降は `touchN > 1` で
砂煙の濃さが **0.42倍**（仕様の「弱めた砂煙のみ」）。

### 発火は `depthM` ではなく `depthShown`
計器の数字は0.55秒の一次遅れで追う。瞬間値で撃つと
**「DEPTH 594.0M」と出ているのに TOUCHDOWN が出る**（実測でそうなった）。
仕様は「HUDのDEPTHが600.0Mに確定する瞬間」なので、**表示している側**に合わせる。
しきい値 `DEPTH_MAX - 0.05` は、小数1桁で "600.0" と出る境目。

### 600m と見出しは同じ場所ではない
実測: 600m に着くのは `sp = 1 / hpR = 0` の時点で、そのとき `#landing` は
**まだ画面の1061px下**にある。「着底したら見出しが出る」と素朴に書くと、
砂煙が消えたあとに見出しが来て**演出と文章が繋がらない**。
→ ライトを 7.5秒引っぱって、見出しが上がってくるまでを照らす役にした。

### 砂煙がレンズを覆って「画面が濁っただけ」になった（2回踏んだ）
1. **撒く場所**。半径 1.1〜5.3m でカメラの真下に撒いたら、板が視界を覆い、
   砂煙あり/なしで**全画素が平均42段暗くなる**のに、絵としては
   「水が濁った」としか読めなかった。→ **視線方向へ 3.2m 送り**、半径も
   1.8〜6.4m に離す。砂煙は「向こうで立っているもの」。
2. **上がる高さ**。最大 3.3m 上げたら目線を越えて浮き、**丸い玉が並んでいる**
   ように見えた。砂は底を這って広がる。→ 最大 1.6m に抑え、板の中でも
   `mix(1.0, 0.30, vUv.y)` で**下を濃く、上をほどけさせる**。

**色は背景より明るくないと霧と区別が付かない。** 最初 `0.088`（＝砂の
アルベド 0.098 とほぼ同じ）にしたら、輝度が背景と一致して形が消えた。
懸濁した砂は光を散らすので **`0.440`** まで上げてある。濃さは `uGain = 0.52`。

判定は目視ではなく差分で採る。`__diag.dustGain = 0` にした絵と引き算すれば
「本当に画素が出ているか」「それが形なのか一様な幕なのか」が分かれる。

### サーチライトは「壁」になりやすい
最初 半径2.6m・丈9.0m・フレネル `pow(…, 2.2)` で作ったら、画面中央を埋める
**乳白色の壁**になった。光の筋は細くて長い。→ **半径1.25m・丈11.0m・
`pow(…, 3.6)`・全体に ×0.34**。さらに `smoothstep(0.0, 0.22, vUv.y)` を掛けて
**コーンの底の硬い楕円の縁**を消す（これが無いと「円盤が浮いている」に見える）。
追加ドローコールは砂煙とライトで **+2**、どちらも強度0の間は `visible = false`。

### 帯は画面中央に置く
`TOUCHDOWN — SEABED` を計器（`#sim`）の並びに置きたくなるが、
**`#sim` は820px以下で `display:none`**。スマホで一番大事な一拍が消える。
→ `#touchdown` は `position: fixed` の**画面中央**に単独で置く。

### ティアごと
| | 砂煙の板 | ライト | 見出しと帯 |
|---|---|---|---|
| high | 16枚 | ON | ON |
| low | **8枚** | ON | ON |
| 品質梯子が2段以上落ちた時 | **0**（出さない） | ON | ON |
| reduced-motion | **0** | **0** | 見出しのみ（帯も出さない） |

仕様の「最低ティアはライトと文字の同期のみ」は、**品質梯子が落ちた端末**
（＝既に重い）がその状態になる。ライトはコーン1枚なので残す。

### reduced-motion では時計そのものを止める（仕様から1点だけ外した）
仕様は reduced-motion を「砂煙と揺れを省き、フェードのみ」としているが、
このリポジトリの `degrade.mjs` は **「reduced では24フレーム空けた2枚が
1画素も違わない」** を合否にしている。帯のフェードとライトの立ち上がりが
残るかぎり画面は動き続けるので、実測で **416画素（帯の1行ぶん・
`box [553,368,174,7]`）** 割れた。
→ `touchArmed && !reduced` で**時計を起動しない**。見出しは
`html[data-anim]` が付かない経路で最初から出ているので、何も足さないのが
正しい落とし方になる。

### 外から観測する口
`__diag.touchdown` が `{t, n, armed, dust, dustAmt, light, lightAmt, tag, head, nDust}`。
`__diag.touchForce = 1.6` で経過秒を固定でき、`__diag.dustCol` / `dustGain` で
色と濃さを差し替えられる（**1セッションで色を振って比べるため**。この環境は
約0.6fps なので、撮り直すたびにブラウザを立ち上げていると1枚15分かかる）。
`__diag.depth.contentTopDoc - innerHeight` までスクロールすると
**`hpR = 0` / `sp = 1` / 深度600** ＝ ちょうど着底の絵になる。

## 弱点4つを潰す — 生物発光・見上げ・縦画面の太陽・魚のシルエット

ACDE の後に実画面を見直して出た弱点への対応。**先に誤診を2つ認めた**:
「スネルの窓が無い」「太陽の道が無い」は誤りで、どちらもシェーダに実装済み
だった。本当の弱点は「実装があるのに画角と振り付けが一度も見せていない」。

### 生物発光 — 薄暮帯の空白を「暗いからこそ見えるもの」で埋める
マリンスノー(motes層)の約16%(`fract(aSeed*7.91)` で選別)が青緑の微光を持つ。
- 深度ゲートは幕と同じ曲線 `ss(0.50, 0.85, depth01)`。薄暮帯から立ち上がる。
- 刺激(bioStim): スクロール速度と ping とクジラの撹乱(vStim=粒の押しのけ量)で
  1 に立ち、約1秒で減衰。静かな時はほのかな明滅だけ。
- **自光なので周囲の減光(depthDim)は掛けない** —— 暗いほど際立つのが正しい。
  経路の吸収だけ通す(遠い光は青く沈む)。
- 係数最大 0.70×(0.06+1.0)≒0.74 で Bloom 閾値(HDR 1.0)の下。「強い発光」に
  しない。発光中は粒を25%大きくする —— **1〜2pxの点は明るくしても読めない。
  大きさが「生きている」を作る。**
- reduced-motion では uTime が凍り bioStimU=0(静的な淡い点になる)。
- 検証口: `__diag.bioStim`(setter・減衰が走るので保持はインターバルで) /
  `__diag.bioState`。

### 陽光帯の見上げ — 実装済みのスネルの窓を初めて画角に入れる
`camera.rotation.x` に `+0.30*ss(0.195,0.235,sp)*(1-ss(0.27,0.33,sp))`。
水に入って一拍おいて機首を上げ、離れていく水面を見送る。
- 窓の縁は水平から41.4°上。素の振り付け(最大+2°)では画角上端(+28°/縦+32°)に
  **一度も入っていなかった**。+0.30radで上端が43.6°/47.6°に届く。
- ★ 2回置き直した。sp 0.05-0.34 → **着水(sp≈0.19)より手前で空を見上げていた**
  (DEPTH 000.0M)。45m → **暖色が吸収で死んでいた**(赤は2単位で落ちる)。
  窓の色が残るのは浅場だけ —— 24〜38m に置いて、最初のカード(0.33)前に返す。
- スクロール駆動の決定的な関数なので reduced でも 0-diff を壊さない。

### 縦画面の太陽 — 「半視野」から方位を決める
`SUN` の方位を初期化時に画角から決める: 横=30°(従来どおり) /
縦=`半視野-1.5°`(円盤が右端に半分掛かる位置)。iPhone縦は半視野≈17°で、
30°の太陽も光の道も**一度も画面に入っていなかった**。
- ★ 「半視野-5.5°」(完全に画面内)で試したら、ハローが画面の4割を洗って
  カードが逆光で読めなくなった。**洗いの正体は3つの合算**: HDRの芯(55倍)を
  Bloomが塗り広げ、ATMOSの水上ベース散乱(0.10)が筋に伸ばし、広域散乱
  pow(s,15)は狭い画角だと画面の大半で0.3〜0.6になる。
- 縦画面だけ: 芯0.32倍(円盤はACESで飽和したまま・にじみの源だけ減る)、
  ハロー指数190→320、広域指数15→34、ハロー/広域の係数0.55倍。
- **決めるのは初期化の一度だけ。** `CAUSTIC_SHIFT` / `RAY_DIR` / `SHAFT_LEN` が
  SUN から一度だけ導出されるので、resize で動かすと海底の集光と光条だけが
  古い太陽を向く。画面回転しても太陽は動かさない。

### 魚のシルエット分化 — 色は霧で最初に死ぬが、形は最後まで残る
3種(銀/黄帯/濃紺)は既にいたが、輪郭が同一で「同じ魚の色違い」だった。
フラグメントの形関数を種の重み(wYs/wNs)で変える:
- 黄帯 = 体高+17%の鯛型(背びれ・尻びれも同率で立つ)、尾は浅い扇(二叉を45%浅く)。
- 濃紺 = 体高-13%の細身、尾は+22%大きく早く開き二叉が35%深い(青物型)、
  尾の拍 0.60倍 —— **大きい種ほどゆっくり打つ。同じ拍だと結局同じ魚に見える。**

## 潜航の4幕・儀式・貫通・浮上（ACDE）

「ポートフォリオとしてもっとカッコよく」への回答4点。提案A/C/D/Eを採用
（B=音は不採用）。全てをつなぐ考えは1つ ——「**計器で海を読む**」の言語を、
色・入口・作品閲覧・出口まで通す。

### A. 深度の4幕 — 21画面おなじシアンだった
実測すると、2画面目から着底まで**21画面が色相185〜195°のほぼ同じシアン**で、
潜っても景色が変わらないから「長い」と感じていた。散乱と光量を深度の関数にし、
0-60m 陽光帯 / 〜330m 中層 / 330m〜 薄暮帯 / 着底(第4幕はサーチライトが受け持つ)
の段を作った。

- **GLSL**: `actScatter(d01)` が SCATTER → 中層 `vec3(.034,.132,.204)` →
  薄暮 `vec3(.013,.048,.106)`、`actLight(d01)` が 1.0 → 0.78 → 0.34。
  段の位置はどちらも `smoothstep(0.10,0.45)` と `smoothstep(0.55,0.95)`。
  ★ **一次の mix にしない** —— 単調なグラデーションは「変化した」と知覚
  されない。段で落とすから幕になる。
- **JS 側の鏡**: `actFog(d01)` が共有 `fogCol` を FOG_SHALLOW → FOG_MID →
  FOG_TWILIGHT の同じ2段で駆動。旧 FOG_DEEP(一次lerpの終点)は**削除**。
  遠景の壁・空との継ぎ目がシェーダの幕と同じ色を見る。
- **光条(シャフト)は薄暮帯で消える**: `1.0 - smoothstep(0.55,0.92,uDepth)`。
  330mに太陽の柱が届いていたら幕が嘘になる。rayAmt も同じ曲線。
- **砂のアルベド** ×`(1 - 0.42*ss(0.55,0.95))`、**GRADE の全画面減光**
  ×`(1 - 0.26*ss(0.55,0.95,uDepth01))`(コントラストの後・汀のリムの前)。
- **★ 吸収(ABSORB)は触らない。** VIS 計器が吸収から視程を解いているので、
  吸収を深度で変えると計器だけが嘘をつく。変えるのは「returns してくる光」だけ。
- **HUD の現在地も幕に合わせる**: SURFACE(<4m) / THE BLUE(<300m) /
  THE TWILIGHT(<520m) / THE ABYSS(`LOC_BLUE/LOC_TWILIGHT/LOC_ABYSS`)。
- 薄暮帯の最終出力は linear 0.056 → sRGB ≒ 67/255。**暗いが黒潰れではない**
  （禁止事項の確認済み）。

### C. 潜る儀式 — 最初のスクロールだけ、水を潜る
ページを**先頭で開いた時だけ武装**（`targetP < 0.012 && !reduced`）。
sp が動き出した最初の1回、浅い暗幕と8個の泡(CSS のみ)が約1.4秒立ち上る。
`#diveVeil` は z-index 4（ping 5 / ヴィネット 6 / 粒 7 / HUD 16 の下）。
- ★ 解除タイマーは **1700ms**。1400ms だと遅延最大の泡
  (delay .30s + 1.30s = 1.60s)がフェード途中でスナップして消える。
  「全員が終わるまで待つ」で決める。
- reduced-motion は CSS 側で `#diveVeil{display:none}`、JS 側も武装しない。二重の栓。

### D. ソナー貫通 — 接触の対象は1人
`CONTACT — <名前> / NNNM` の1行を、クジラだけでなく**作品カード**にも出す。
- 優先順位: クジラ(UNKNOWN)が最優先(珍しい方が勝つ)。いなければ近傍の
  可視カード。**入り 7.0 / 出 8.2 のヒステリシス**で境目のチラつきを止め、
  正面判定 `dot > 0.10`、区間は `sp∈(0.03,0.92) && hpR < 0.30`。
  ★ 上限 0.92 —— 着底間際まで許すと TOUCHDOWN の一拍に CONTACT が重なり、
  いちばん静かであるべき瞬間が騒がしくなる。
- 距離はクジラと同じ専用の尺 `WH_SONAR_M = 4.2`、読み直しは同じ `SN_TICK` 0.45秒。
  **対象が替わったら掃引の時計を仕切り直す**(snClock=0)。
- タップ/クリックで**ソナーの波紋**(ping)を1つ放ち、クリック方向の視線上に
  いる魚を驚かせる(既存の `fStart` を使い回す)。演出は既存部品の再配線だけ。

### E. 浮上 — 出口も体験の一部
本文の連絡先ブロックの末尾に `RESURFACE — 浮上する ↑`。3.2秒の
easeInOutCubic を rAF で回して先頭へ戻す。
- **浮上の途中で急速モードが点くのは意図した動き**: 文言は向きで
  `RAPID ASCENT` に替わり、泡は下へ流れ、RATE は負を振る。浮上が一番
  速い所で計器が総出になる —— これが「出口も計器で読む」の答え。
- 途中でユーザーが操作したら即座に手を放す: wheel / touchstart / keydown /
  pointerdown の4系統に once で stop。**連打ガード**(`if (resurfacing) return`)
  が無いと rAF ループが2本走る(レビューで発覚)。
- reduced-motion は即 `scrollTo(0,0)`。JS無効は素の `href="#"` で先頭へ。

### 敵対レビューで直した6件
実装後に4視点(GLSL/JS/回帰/設計)の敵対レビューを回して出た確定欠陥:
1. `__diag` に `get dive()` が二重定義され、新設の観測口が死んでいた
   (後勝ちで旧が生存)→ 新設側を `diveRitual` に改名。
2. 砂が「媒質の幕」と「光量の幕」で**二重に暗くなる** → `waterFogV` の
   light 引数を分離し、reach はコースティクス/光溜まりだけに掛ける。
3. FOG_DEEP が死値のまま残り、コメントが旧仕様を語っていた → 削除・書き換え。
4. resurface の再入と中断漏れ(キーボード/スクロールバー) → 上記ガード4系統。
5. 儀式の解除 1400ms が最遅の泡を切る → 1700ms。
6. カード接触のヒステリシス(`cardContactI`)がクジラ登場時と接触なし時に
   持ち越される → 両分岐でリセット。

## 航海計器とレティクル — 動かない数字は計器に見えない

参考にした [The Sea We Breathe](https://www.awwwards.com/sites/the-sea-we-breathe)
（Blue Marine Foundation / Green Chameleon）の説明にある核心は
**"inspired by navigational interfaces to create a head-up-display-styled UI"**。
汀ノ庭は元からこの系統なので、足したのは計器の density だけ。

### 出す値は「シーンから実際に計算できるもの」に限る
| 表示 | 出どころ | 実測での振れ |
|---|---|---|
| RATE（降下速度） | `lastDepthM` の時間差分を 0.45s で平滑化 | 0 〜 75M/S |
| PITCH | `camera.rotation.x` の実値 | -03.4° 〜 +08.5° |
| SEA | `surfaceY(camera.xz, waveT)` の瞬時値 | -0.34 〜 +0.36M |
| VIS | 媒質の吸収から「輝度が10%に落ちる距離」を解く | 51 〜 89M |
| TEMP | **計算のもとが無い**。DEPTH と同じ演出上の数字 | 24.2 〜 4.8℃ |

`VIS` はシェーダの `turbidity()` と**同じ式**を JS 側に持つ。片方だけ変えると
「絵は変わっているのに数字が動かない」＝計器だけが嘘をつく状態になる。

### 方位計(HDG)を入れて、外した
最初 `HDG 214.0°` を出した。カメラのヨーを足せば針路を保つ計器に見えるはず
だったが、**この場面のカメラは向きを変えずに降りるだけ**で、実測の振れ幅は
**0.0°** ——「常に 214.0 を表示するだけの飾り」だった。降下速度へ差し替えた。
**動かない数字は計器に見えない。** 何かを足す前に、まずそれが動くか測る。

### そのとき私は計測を2回まちがえた
1. 壁時計で10回サンプリングして「振れ幅0.0°」と結論した。この環境は約0.6fps
   なので、**10回とも同じフレームを読んでいた**。`__diag.frames` が進んだ時だけ
   読むようにしたら、RATE は 0→75 と振れていた。
2. 計器の更新を「45フレームごと」(FPS表示と同じ場所)に置いた。1fps の端末では
   45秒に1回しか更新されず、深度が361Mでも水温が112M地点の値のまま止まった。
   **更新の刻みはフレーム数ではなく実時間**（0.2秒）。

このリポジトリで同じ罠を踏むのは3度目（`degrade.mjs` の壁時計、`waitDot` の
「動き出す前の静止」、そして今回）。**「変化を見る」計測は、必ずフレームで区切る。**

### レティクル
画面中央の人工水平儀。`camera.rotation.z` で傾く。中央に置くので、どの画面幅でも
文字の領域と取り合わない（モバイルで計器を増やせない理由がここだけ無い）。
潜っている間だけ出す（`sp` 0.06→0.22 で現れ、0.86→0.99 で消える）。
★ **スマホではポインタが無いので実測ロールは 0.0000 のまま**＝傾かない。
枠として機能はするが、「傾く水平儀」はPCだけの体験だと理解しておくこと。

### 一次遅れは 0 にならない（reduced-motion を割った）
RATE の平滑化を素の一次遅れで書いたら、値は 0 へ**漸近するだけで 0 にならない**。
表示は小数1桁なので `+00.1` と `+00.0` の境目を延々と跨ぎ、**止まっているのに
数字がちらつく**。これが `degrade.mjs` の「reduced-motion で差分0画素」を実際に
割った（実測: 計器の位置に 48画素・maxDelta 19 の差）。
→ `|rateSm| < 0.05` で 0 に落とす。止まったら止まったと出す。

**HUDに動く数字を足したら、必ず degrade を回す。** 「動きを止めた状態でも
動くもの」を増やしたことになるので、ここが最初に壊れる。

### 桁あふれ
RATE は表示だけ ±99.9 で頭打ちにする。描画が詰まった端末では1フレームの落差が
大きく、実測で 75M/S が出た。値ではなく**表示**を止める（計器の桁がずれると読めない）。

## 実機で測る — `?bench=1`

**この開発環境では iOS Safari を再現できない。** 事実として確認したこと:

- `npx playwright install webkit` は **403**。ゲートウェイが `cdn.playwright.dev` と
  Microsoft ミラーへの CONNECT をポリシーで拒否する（`curl "$HTTPS_PROXY/__agentproxy/status"`
  の `recentRelayFailures` に残る）。
- npm 経由も不可。`playwright-webkit` は展開後 **16KB のラッパー**で、中身は同じCDNを叩く。
- apt の `libwebkit2gtk` は入るが、**Playwright はシステムの WebKitGTK を操作できない**。
- そして仮に入っても **iOS Safari ではない**。Playwright の WebKit は Linux 向けビルドで、
  JavaScriptCore は共通でも描画スタックが別物。実機で効くのは
  「WebGLコンテキストの上限とメモリ逼迫による剥奪」「Metal裏打ちのANGLEとの差」
  「URLバー開閉によるビューポート高の変動」「発熱によるクロック低下」——
  **どれも Linux 版では再現しない**。

→ **端末に自分で測らせる。** `?bench=1` を付けて開き、ボタンを押すと約34秒
ページを自動スクロールしながら計測し、コピー/共有できるテキストを出す。

### 作るときに踏んだこと（同じ罠を踏まないために）
1. **文書の高さで時間を按分しない。** 本文が全体の大半を占めるので、
   潜航が数秒で通り過ぎて「潜航(深)」の標本が**0枚**になった。
   潜航に 62%、本文に 38% と決め打ちで配る。
2. **区間の判定に `sp`（潜航の進捗）を使わない。** `sp` はスクロールへ一次遅れで
   追うので、フレームレートが低い端末では追いつく前に本文へ入り、やはり
   「潜航(深)」が0枚になる。**`scrollY` で判定する**（遅れが無く、そのフレームで
   実際に描いた場所そのもの）。
3. **暖機は「秒」ではなく「枚」で捨てる。** 「最初の1秒を捨てる」と書いたら、
   遅い端末では1秒＝1枚しか進まず、シェーダのコンパイルの **19秒のフレーム**が
   そのまま「最悪1枚」に出た。20枚捨てる（実時間4秒を上限に）。
4. **パス別コストは整合しない時に出さない。** 構成を切り替えて差分を取る方式なので、
   フレームが不安定だと符号ごと壊れる（実測で **Bloom が合計の13倍**）。
   検算して合わなければ「測定不能」と出す。**嘘の数字を渡す方が、無いより悪い。**
5. **計測中はパネルを `display:none` にする。** 半透明の板を被せたままだと、
   その合成ぶんが数字に乗る。進捗は `pointer-events:none` の小さな札1枚だけ。

### ついでに直したもの
`window.__ctxLost` を**立てる側がどこにも無く**、`verify.mjs` の
「context lost 0回」は常に素通りしていた。`webglcontextlost` を実際に数える。
iOS はメモリ逼迫でコンテキストを取り上げるので、実機計測ではここが本命の指標。

## 縦画面のヒーロー — 主役を水平線に貼り付けない

カードの配置は `[x, y, z, ヨー, 倍率]`。**倍率を1枚ごとに持たせている**のは、
縦画面で1枚目だけ大きくしたいため —— 全体に掛けると水中の2枚目まで巨大になる。

1枚目は元々 `z=-8.40 / 倍率 0.66`。デスクトップ（`-5.35 / 1.00`）に対して
**見かけの大きさが 2.4分の1**しかなく、実測で画面幅の 42%。しかも水平線際に
貼り付いていて、下に空の水面が画面の1/3残っていた。`-6.70 / 0.86` に寄せて
**幅の 70%**（275×156px / 390×844）にしてある。

カードがCTAの下端より上へ出ないことは `solvePortraitLift()` が仰角を二分探索で
解いて保証するので、**大きくしても文字には被らない**。逆に言うと、大きくすると
仰角が上がって空が増えるので、`node scripts/probe.mjs --script=scripts/hero-shot.mjs` で「カードの幅の割合」と「CTA下端」を必ず一緒に測ること。

## 「止まるまで待つ」テストは、動き出す前に止まったと判定する

`verify.mjs` の目次の検査（針・行・見出しの3点一致）が**たまに落ちる**状態だった。
症状は `dotY` が1つ前の節の位置のまま返り、`readP` と `now` は正しい、というもの。
再実行すると通るので長らく「環境が遅いせい」に見えていた。

原因は `waitDot()`。「フレームが進んだうえで位置が動いていない」を条件にしていたが、
`lastF` の初期値が `-1` なので**最初の1サンプルが必ず「フレームが進んだ」と判定**される。
針がまだ動き出していなければ、そこから3回続けて同じ値を読んで「止まった」と結論する。

→ 針は `readP` へ一次遅れで追うので、**「動き出してから止まるまで」**を待つ。
動く必要が無かった場合のために、フレームが6つ進んだら動かないまま抜けてよいことにする。
修正後は3回連続で 5/5 一致。

**教訓**: 「変化が止まるまで待つ」ループは、**変化が始まる前**の静止と
**終わった後**の静止を区別できない。開始を検出する条件を必ず入れる。
（`degrade.mjs` の「壁時計で待つと約1fpsでは収束を動きと取り違える」と同じ系統の罠。）

## 波 — 「傾きが白色雑音」だと打ち出した金属板に見える

水面が金属板に見えていた原因は、振幅でも解像度でもなく**傾きスペクトルの形**。

頂点の Gerstner は 21/10.5/5.2/2.5/1.25m に steep 0.075/0.150/0.140/0.115/0.085。
`steep` はほぼ傾きそのものなので、**どの波長帯もほぼ同じだけ傾いていた**。
オクターブごとの傾きが一定＝傾きが白色雑音。断片シェーダの細波も同じで、
`ripple()` が返す傾き `am*fr` は 0.130/0.175/0.180/0.195/0.192 とやはり平ら。
実際の海の傾きスペクトルはピーク波長を境に高周波側へ落ちる。

**もう1つ、うねりが無かった。** いちばん長い波が 21m・振幅 0.25m で、
カメラ高さ 0.95m から見ると面がほぼ平ら。細かい皺が乗っているだけだった。
46m・振幅 0.40m を足して、面そのものが上下するようにした（合計 0.68m → 0.95m）。

| | 旧 | 現 |
|---|---|---|
| 波長 | 21 / 10.5 / 5.2 / 2.5 / 1.25 | **46** / 22 / 10.5 / 5.2 / 2.5 / 1.25 |
| steep | .075/.150/.140/.115/.085 | .055/**.085**/.095/.072/.050/.032 |
| 細波の傾き合計 | 0.87（平ら） | **0.42**（高周波ほど落とす） |

### 「近くは細かく、遠くは滑らか」を一律の減衰でやろうとしない
水上の面は長らく `g = (g + gn) * fade`（`fade = exp(-d*0.055)`）で
**全帯域を同じ係数**で落としていた。傾きを高周波側へ落としたあとにこれを
併用すると、今度は**近景から細波が消えて低周波の大きな瘤だけが残り、油膜**に
見える。とくにモバイルは被写界深度が無く手前がぼけないので露骨に出た。

→ 水中の天井で既に使っていた `rippleD`（`exp(-dist*fr*0.0090)` で**波長ごとに**
落とす）を水上でも使う。近景に 4cm の細波が残り、遠景では自分から消えるので、
「鋭い太陽のスペキュラがモアレる」という当初の懸念も同時に消える。
実効傾きは d=3m で 0.135/0.100/0.074/0.050/0.032、d=15m で 0.104/0.059/0.029/0.010/0.002。

### 正弦波は5本足しても周期的
`ripple()` は純粋な正弦波なので、何本重ねても模様が規則正しく整う。
不規則さは vnoise の勾配 1本（周期 0.5m）だけで、崩し方が粗すぎた。
細かい方（0.14m）を1オクターブ重ねて周期を壊す。**距離で早めに殺す**こと
——遠景まで残すと 1画素を切ってモアレ（籠の網目）になる。

### 波を触ったら必ず測るもの
`WAVES` を変えると `surfaceY` の最大値が変わる。魚と粒子の水面クリップは
`WAVE_H` から自動生成されるので追従するが、**`__diag.fish.sky` が `{n:0}` の
ままか必ず測り直す**（`scripts/sea-shots.mjs` が各地点で出力する）。

## アクアリウム — 「夕暮れの外洋」から「大水槽」へ

**海中は水族館の大水槽。** 以前は「夕暮れの外洋を600m潜る」設計で、
暗く・濃く・魚をほとんど出さない作りだった。方針が変わったので、
そこに合わせて入っていた仕掛けを一つずつ外してある。
**元に戻したくなった時のために、外したものを全部ここに書く。**

### 水そのもの（`G_MEDIUM`）
外洋の深場の水は濃く、コード中の実測メモのとおり **3.45m でも光の約96%を吸う**。
数メートル先が闇なので、魚を何匹足しても見えない。水槽は濾過された水を
上から強く照らすので 20m 先まで見える。変えたのは3つだけ。

| | 外洋(旧) | 水槽(現) |
|---|---|---|
| `MEDIUM_K`（減衰率） | 0.47 | **0.165** |
| `SCATTER`（散乱して返る色） | 0.028,0.115,0.148 | **0.052,0.196,0.246** |
| `farFade`（霞み切る距離） | 7→38m | **16→86m** |
| `dl`（深さで届く光） | →0.16 | **→0.72** |
| `FOG_DEEP` | 0.0035,0.0195,0.0380 | **0.0230,0.0930,0.1400** |

`ABSORB` の比は**触らない**。赤から先に吸われるのは水である以上同じで、
ここを崩すと水ではなく色付きの空気になる。
明るさをこの3つ以外で足さない。個々の材質に色を盛ると、同じ距離の魚と
カードで霞み方が違う状態に逆戻りする。

### 「間合い」の仕掛けを外した（ここが一番効いた）
魚が見えなかったのは水の濃さではなく、**見せない作りが3つ入っていた**から。
匹数を 15 → 46 に増やしても絵が変わらず、初めて気付いた。

1. `budget = round(4 - 2*ss(0.30,0.62,sp))` … 濃く描けるのは **2〜4匹だけ**で、
   残りは alpha 0.04 に固定。→ `fishBudget`(既定 999)だけにした。
2. `want = 0.34 + 0.66*ss(0.18,0.55,r)` … **画面中央ほど薄れる**（周辺視の実装）。
   → `0.90 + 0.10*…`。端がわずかに濃いのだけ残す。
3. `fPos[o+1] = cam.y + down*(0.3 + rnd*0.35*zd)` … 進行方向の**片側にだけ**湧く。
   底(cam.y -9.4)では `down=-1` で**砂の中へ湧いて**おり、最深部は画面に2匹しか
   居なかった。→ カメラの高さを中心に上下へ散らし、砂と水面の間に収める。

実測（desktop・46匹）: 画面内 25〜40匹 / うち濃いもの 15〜33匹 / 最も遠い個体 33m。

### 種を作る（`aSp`）
1種だけだと、何匹居ても「同じ魚を量産した」に見える。**水槽らしさは匹数より
種類の差**で出る。0=銀のアジ型(58%) / 1=黄帯(30%) / 2=濃紺の大きめ(12%)。
**色だけ変えて寸法が同じだと塗り替えに見える**ので、`fSize` を種に紐づける。
色素は腹 0.235 → **0.56 前後**まで持ち上げた（旧値は夕暮れの外洋用で、明るい水に
置くと切り絵のシルエットになる）。黄帯は**体側の1本**に留める —— 面で塗ると
熱帯魚のおもちゃになる。

### 明るくすると見えてくるもの（暗い海では気付けなかった）

## 空に出さない（魚・マリンスノー）

粒子はカメラを中心とした帯の中で巻き戻す（`yMax` は +0.4/+0.2/+0.2 で、
層がカメラに追従する）ので、水面付近ではワールド座標で **y=+1.35** まで
上がる。魚も `cam.y + down*(0.3 + rnd*0.35*zd)` で **+4.5** まで出る。
一方 water の `position.y` は 0 のままで、Gerstner の変位を全部足しても
**±0.68m** にしかならない。＝どちらも空を飛ぶ。

→ 高さだけの Gerstner を **1本**にまとめた（`WAVES` から `WAVE_H` を作り、
GLSL 側 `G_SURF` の `surfY()` と JS 側 `surfaceY()` を**同じ表から生成**する）。
- 粒子は頂点シェーダで `vFade *= 1.0 - smoothstep(sy-0.50, sy-0.08, wpos.y)`
- 魚は `FISH_SUB = 0.42` を**4か所**で当てる（湧き / hero1 のNDC配置 /
  目標 `ty` / 積分後の最終クランプ。最後のは上向きの速度も殺す）
- 水は `uTime = t*0.8`、粒子は `t` を使うので、`uWaveT` は**別に**渡す。
  JS 側は `waveT` をモジュール変数に置いて `updateFish` と共有する
  （`frame()` の `const T` はローカルなので `updateFish` から見えない）
- 測る口は `__diag.fish.sky` = `{n, worst}`。**n が 0 でなければ飛んでいる。**

## 汀線の検査は「固定フレーム待ち」で合否が入れ替わっていた

`0.60以降は帯を描かない` が iPhone の回だけ落ちた。値は
`uL 0.002 / uR 0.004`（許容は 0.002）。再実行すると `0.001 / 0.002` で通る ——
**合否が実行ごとに入れ替わる状態**だった。

原因は帯の側ではなく**測り方**。`hp` は `hpR` へ一次遅れ（`lag1 0.09s`）で
追うのに、標本を `waitFrames(5)` の固定フレーム数で採っていた。追いつく前に
読んだ回は `hp ≈ 0.5955` で、`1 - ss(0.50,0.60,hp)` の裾が 0.004 残る。

→ **frames ではなく「`hp` が `hpR` に追いついたか」で待つ**（`waitSeam()`）。
`waitDot()` で一度やった直し方と同じ。直したあとは3回とも
**`uL:0 / uR:0` ちょうどゼロ**で、裾ではなく本当に消えていることが分かった。

**「許容内だからOK」で流さない。** 許容の縁で揺れているなら、
測り方が間違っているか、実装が縁に乗っているかのどちらか。

## reduced-motion の「1画素も動かない」から、実測の計器だけ外す

`degrade.mjs` の REDUCED は **24フレーム空けた2枚が1画素も違わない**を
合否にしている。ここが `48画素 / maxDelta 19 / box [1200,187,18,7]` で落ちた。
場所は `#sim` の最終行 —— **`DPR ×1.0 — 60/60 FPS`**。

これは絵の話ではない。FPS の表示は45フレームごとに**実時間から**更新されるので、
シーンが完全に静止していても数字だけは変わる。同じ形の差分は RATE の桁でも
一度踏んでいる（そちらは値にデッドバンドを入れて直した）。

→ その行だけ `<span id="simTel">` で包み、degrade 側で
`#simTel{visibility:hidden}` を当ててから撮る。
**RATE / PITCH / SEA / VIS / TEMP は隠さない** —— あれらはシーンから導く値で、
reduced-motion で動いたら本当に不合格。隠すのは実測の計器1行だけ。

`visibility:hidden` にするのは、`display:none` だと行が詰まって
レイアウトが変わり、比較そのものが別物になるため。

## `verify.mjs` は `--src=` を忘れると「別のページで全項目PASS」を出す（直した）

`--src=` の既定値が `public/lab/trexworks_umiatari_v6.html` だったので、
**`node scripts/verify.mjs` とだけ打つと汀ノ庭を1度も開かないまま

→ **`--src=` を必須にした**（無ければ exit 2）。加えて
判定表の先頭に対象ファイルを出し、末尾で
`※ 判定なし N件 —— 合格ではない` と数えて並べる。
`seam` が取れなかった時は `--src=` の指す先を疑えと1行足す。

正しく `--src=public/migiwa/index.html` を渡した時に残る `—` は3つだけで、

合否にしない）/ **ヒーローが縦画面で被っていない**（横長では該当しない）/

**n/a は合格ではない。** このリポジトリでは同じ形の事故を3回踏んでいる
（`window.__ctxLost` を立てる側が無く「context lost 0回」が常に真だった件、
ヘッドレスChromiumの既定 reduced-motion で「演出が動いていない状態」を
正常と読んだ件、そしてこれ）。**「測れた」と「通った」を必ず分けて出す。**
