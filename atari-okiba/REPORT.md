# 納品レポート — あたり置き場

## 勝手に決めた前提(要確認事項)

依頼の「不明点は妥当なデフォルトで決めて完走する」に基づき、以下を独断で決めました。
変更したいものがあれば指示してください。

| # | 決めたこと | 理由 |
|---|---|---|
| 1 | 置き場所はリポジトリ内の `atari-okiba/` サブディレクトリ | 既存のNext.jsサイト(becool)を壊さない自己完結構成にするため |
| 2 | 管理画面の認証は「Basic認証(ユーザー名任意/パスワード=ADMIN_TOKEN)」 | ブラウザが同一オリジンfetchに認証を自動付与するため、JS側でトークンを保存せずに済む(localStorage漏えいリスクの排除)。curl/テスト用に `Authorization: Bearer` も併用可 |
| 3 | スラッグは `^[a-z0-9][a-z0-9-]{0,62}$` に制限 | URL・R2キー・レスポンスヘッダ(realm)に安全に埋め込むため |
| 4 | 閲覧パスワードはsalt付きSHA-256で保存(PBKDF2等は不使用) | Basic認証は全アセットのリクエストごとに検証が走るため、無料枠のCPU制限(10ms/リクエスト)と両立させる割り切り。確認用URLの簡易保護という用途に見合う強度 |
| 5 | 確定済みバージョンは変更不可(追記・再finalize不可) | 「過去版がそのまま残る」ことを構造的に保証するため |
| 6 | アップロード途中で失敗した版は「未確定の欠番」になる | 最新URLを壊さない安全側の設計。番号が飛ぶだけで実害なし |
| 7 | 表示名変更・閲覧パスワードの後から変更(PATCH)は実装、案件の削除は未実装 | 削除はR2の大量削除とサブリクエスト上限が絡むため将来課題とした |
| 8 | 管理画面の一覧表示は40案件まで | 無料プランのサブリクエスト上限(50/リクエスト)内に収めるため |
| 9 | 1ファイル95MB上限、パス1024文字・40階層まで | プラットフォーム上限(100MB)の安全マージンと異常系対策 |
| 10 | `.DS_Store` / `Thumbs.db` / `desktop.ini` は自動スキップ | Mac/Windowsのゴミファイル対策 |
| 11 | 配信サイト直下の `v/<数字>/` パスはバージョンURLとして予約 | 依頼のURL形式(/p/slug/v/n/)を固定とした帰結。README・DESIGNに制約として明記 |
| 12 | 単一フォルダのD&Dはフォルダ名の階層を剥がして展開 | 「site/index.html」ではなく「index.html」がルートに来る、直感に合う挙動 |
| 13 | R2バケット名は `atari-okiba-files`、Worker名は `atari-okiba` | README のコマンドと wrangler.jsonc を一致させるため(変更可) |
| 14 | 管理画面HTMLはTypeScript内の文字列として保持 | 「ビルド工程なし」を厳守しつつ、wrangler・vitest両方で追加設定ゼロで動かすため |
| 15 | 最新URLは `Cache-Control: no-cache`、版URLは `max-age=3600`(パスワード付きはprivate) | 「同じURLで最新が出る」ことを最優先。確定版は不変なので軽くキャッシュ |
| 16 | 日本語ファイル名はNFC正規化して保存・照合 | MacのD&D(NFD)とURL(NFC)の不一致で404になる事故を防ぐ |

### セキュリティレビューで修正した項目(1周目 should-fix)

| ID | 指摘 | 対応 |
|---|---|---|
| F1 | `fetch`ハンドラの`try`内が`await`なしで非同期例外を捕捉できず、500ページがデッドコード化 | 各ハンドラ呼び出しを`return await`に変更 |
| F2 | `/p`配信の成果物HTML/SVGが同一オリジンで実行され、Basic資格の自動再送で管理APIを乗っ取れる | Basic認証経由の`/api`に`/admin`由来Referer検証を追加(Bearerは対象外)。`/admin`のReferrer-Policyを`same-origin`に |
| F3 | relパス長がUTF-16文字数基準でR2キーの1024バイト上限と不整合(未認証URLでR2例外を誘発可) | UTF-8バイト長(900B上限)で判定 |

### accepted-risk として据え置いた項目(理由はDESIGN.mdの制約表に記載)

- **存在オラクル(401 vs 404)**: 構造上ほぼ不可避。スラッグに機微な顧客名を使わない運用で回避。
- **閲覧パスワードのSHA-256(1回)**: KV読み取り漏えいが前提で、その状況ではR2本体も読めて保護は無意味。CPU 10ms制約との両立のためPBKDF2は不採用。将来課題(HMAC署名Cookieキャッシュ+PBKDF2)を明記。
